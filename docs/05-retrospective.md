# 实现复盘

本复盘基于项目的实际实现与验证记录，由 AI 协助整理措辞。候选人已确认亲自完成代码验证，实际投入约 2 小时；代码生成、自动化运行和问题修复的分工见 [AI 使用说明](04-ai-usage.md)。

## 最难的问题

难点是同时做到“模型可以自主选择动作”和“模型无法越权保存”。若 Runner 固定所有业务分支，就无法证明模型决策；若直接信任模型，又可能把冲突时段、未确认变更或保存失败描述为成功。

当前分工是：模型选择工具与结束动作，通用 Runner 只处理调用循环；保存工具强制检查授权、审核和占用；最终结果根据执行账本核验。模型声称的完成状态不能覆盖实际数据库结果。

## 实现中修正的细节

1. 故障注入放在插入之后、提交之前，以验证真实回滚，而非仅返回一个失败字符串；一次性故障需被消费，后续显式尝试才可能成功。
2. 查询成功不代表保存时仍无冲突，因此保存事务内必须重新检查占用。
3. 唯一键只防止同请求重复创建，不能防止不同请求抢占相同时段；使用写事务序列化检查与插入，并加入并发测试。
4. 幂等返回是原草稿的存在证明，应标注原保存审核范围，避免被误认为按最新规则重新审核。
5. 保存失败后再读取素材，不应丢失失败事实；保存错误与普通工具错误分开保留。
6. 达到调用上限但此前已保存时，同时返回任务未完成和实际已保存回执，避免用户因误以为未保存而重新创建。

## 技术取舍

- 自定义 Runner 让决策循环易于解释和检查；没有引入当前规模不需要的工作流框架。
- 标准库 HTTP 适配器减少安装成本；代价是只支持较窄的工具调用协议，不具备完整 SDK 的兼容能力。
- 合成规则与数据让测试可确定复现；其通过不意味着真实素材安全审核有效。
- 选择 unittest 而非额外安装测试框架，保证当前离线环境可直接运行。

## 学习收获

通过亲自验证这个项目，我对 Agent 的关注点从“能否给出一个结果”转向“每个结果是否有执行证据”。模型说已保存，并不代表数据库真的提交成功；工具回执、草稿 ID 和实际记录必须对应。

我理解了模型决策与确定性校验的分工：模型可以根据风险、冲突和失败选择下一步，用户授权、数据完整性和保存权限则应由代码约束。这样既保留动态决策，也能避免模型自行改变硬性要求。

我也区分了幂等与并发冲突保护。唯一键能防止同一请求重复创建，但不同请求仍可能争抢同一时段；查询时没有冲突，也不能替代保存事务中的再次检查。

验证方法本身同样需要审查。一次查询多个候选后选择空闲时段，也是有效决策路径；测试应检查业务语义和观察后的动作，而非强制固定调用顺序。已有测试全部通过，也可能遗漏“保存失败后再出现其他错误”这样的组合场景。

这次 AI coding 的经验是先明确范围、输入输出和验收点，再通过运行结果和 Trace 检查生成代码。学习与复盘关注已发生的问题和验证依据，不把 Mock 通过当成真实模型能力证明。

## 当前不足与下一步

后续代码评审又复现了“保存失败被后续工具错误覆盖”和“无可行时段判断越过授权范围”两个问题。独立记录保存结果、限定候选集合后，新增结束拒绝反馈，使模型有机会在剩余预算内自纠。最终状态仍由工具事实核验，拒绝反馈不会替模型执行保存。

真实复测还发现评估本身需要改进：模型可在一次查询中观察冲突和可用候选，再作调整。强制要求第二次查询会误判正确业务路径。因此评估改为核对原时段冲突、所选时段的可用证据，以及发生在观察之后的保存或待确认动作；同时加入缺少冲突观察、先保存后观察、后续占用等反例测试。

最初两轮真实模型评估中，首轮一个场景在模型请求/协议阶段失败，旧日志没有细分原因，不能事后断言具体服务端错误；另一个场景中模型把 flexible 窗口误认为需要额外确认，可信账本正确返回未完成。随后明确窗口内已有授权、设置较低采样温度并细分安全错误分类，第二轮 12/12 通过。没有放宽确认边界或改写失败记录。

环境接入中还发现 macOS 的 Python 没有可用默认 CA 路径，系统 CA 可验证同一服务。客户端仅在默认 CA 不存在且无用户显式覆盖时使用 `/etc/ssl/cert.pem`，始终保持证书与主机名校验，并允许显式指定 `AGENT_CA_BUNDLE`。

下一步可针对更多合成数据与重复运行评估稳定性；当前一次完整通过不等于所有输入或模型未来版本都可靠。

之后可增加人工确认后的跨进程恢复、更多渠道与时段规则。当前不承诺这些能力，先保持核心验收链路完整。
